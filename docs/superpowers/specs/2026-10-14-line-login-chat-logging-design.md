# LINE Login และการจดรายรับ-รายจ่ายผ่านแชท LINE

- วันที่: 2026-10-14
- สถานะ: รอรีวิว
- branch: `feature/line-login-chat`

## 1. เป้าหมาย

ผู้ใช้จดรายรับ-รายจ่ายได้จากแชท LINE โดยไม่ต้องเปิดแอป และ login ด้วย LINE ได้ ระบบแยกข้อความที่พิมพ์มาเป็นรายการและใส่หมวดให้เอง

### สิ่งที่เจ้าของโปรเจกต์กำหนด

- มีทางเข้าสองแบบ: LINE และอีเมล/รหัสผ่าน (แบบเดิม) แต่ให้ LINE เป็นทางหลักที่เด่นกว่า เพราะจดผ่านแชทได้
- จดผ่านแชทได้ทั้งรายรับและรายจ่าย ข้อความเดียวมีหลายรายการได้ เช่น `ค่าข้าวตอนกลางวัน 50 บาท ค่าน้ำ 100 บาท ค่าเน็ต 20 บาท`
- **ต้องฟรีทั้งหมด** ไม่มีบิลรายเดือน จึงแยกหมวดด้วยกฎกับพจนานุกรม ไม่ใช้ AI
- ถามวันก่อนบันทึกทุกครั้ง ยกเว้นพิมพ์วันมาในข้อความแล้ว
- รายการที่ระบบมั่นใจบันทึกทันทีหลังเลือกวัน ส่วนคำที่ไม่รู้จักให้ผู้ใช้เลือกหมวด
- ระบบจำหมวดที่ผู้ใช้สอนหรือแก้ไว้เป็นรายคน
- บอทถามยอดได้ (`สรุป`) และระบุวันในข้อความได้
- จำกัดจำนวนการใช้งานต่อคนเพื่อกันสแปม และปรับเกณฑ์ได้โดยไม่ต้องแก้โค้ด

### เกณฑ์ว่าสำเร็จ

1. กดเข้าสู่ระบบด้วย LINE จากหน้าเว็บได้ ถ้ายังไม่มีบัญชี ระบบสร้างให้ และพาไปเพิ่มเพื่อนบอทในขั้นตอนเดียวกัน
2. บัญชีอีเมลเดิมกดเชื่อม LINE ในหน้าตั้งค่าได้ แล้วจดผ่านแชทเข้าบัญชีเดิม
3. พิมพ์ `ค่าข้าวตอนกลางวัน 50 บาท ค่าน้ำ 100 บาท ค่าเน็ต 20 บาท` → บอทแสดง 3 รายการ (อาหาร/เครื่องดื่ม, ค่าน้ำ/ไฟ/เน็ต/โทรศัพท์, ค่าน้ำ/ไฟ/เน็ต/โทรศัพท์) แล้วถามวัน → กด "วันนี้" → บันทึกครบ 3 รายการ และเห็นใน dashboard
4. แอปยังอยู่ในโควตาฟรีของ Firebase Spark, Vercel Hobby และ LINE Messaging API

## 2. ขอบเขต

**ทำในรอบนี้:** LINE Login, การเชื่อมหรือยกเลิกการเชื่อมบัญชี, การปรับหน้าตั้งค่าสำหรับผู้ใช้ LINE อย่างเดียว, บอทจดรายการ (ถามวัน, ถามหมวด, แก้หมวด, เลิกทำ), คำสั่ง `สรุป` และ `วิธีใช้`, พจนานุกรมกลางและพจนานุกรมส่วนตัว, การจำกัดจำนวนการใช้งาน, เอกสารการตั้งค่า

**ไม่ทำ:** AI แยกข้อความ, ข้อความที่บอทส่งเอง (push) เช่น แจ้งเตือนงบ, Rich menu, LIFF, การรวมข้อมูลสองบัญชี, การแสดงว่ารายการมาจาก LINE บนเว็บ, การจำคำจากการแก้บนเว็บ, การอ่านสลิปหรือรูป, การใช้อีเมลจาก LINE

## 3. สถาปัตยกรรม

```
 หน้าเว็บ (CRA เดิม)                          Vercel Functions (ใหม่, โฟลเดอร์ api/)
 ───────────────────                         ─────────────────────────────────
 [เข้าสู่ระบบด้วย LINE] ── POST ───────────▶  api/auth/line/start     ──▶ LINE Login
 [เชื่อม LINE] (ตั้งค่า)                        api/auth/line/callback  ◀── redirect กลับ
 /auth/line ◀── #token=custom token ─────────       │ ตรวจ ID token, หา/สร้างบัญชี
   └ signInWithCustomToken                          ▼
                                               Firestore (firebase-admin)
 แชท LINE ── webhook ────────────────────▶   api/line/webhook               ▲
                                               └ ตัวแยกข้อความ (โมดูลล้วน) ───┘
```

- **ฝั่ง server** ใช้ Vercel Functions ใน repo เดิม deploy ไปพร้อมเว็บ ไม่ใช้ Firebase Cloud Functions เพราะต้องใช้แพ็กเกจ Blaze
- **วิธีเชื่อม LINE กับ Firebase Auth** ให้ server ออก custom token เอง ไม่ใช้ OIDC provider ของ Firebase เพราะต้องอัปเกรดเป็น Identity Platform และยังไม่แน่ใจว่าจะทำงานกับ LINE ได้ราบรื่น
- **ช่องทาง LINE**: LINE Login channel กับ Messaging API channel ต้องอยู่ใต้ Provider เดียวกัน ตามเอกสาร LINE แบบนี้ userId ที่ได้จากทั้งสองช่องทางจะตรงกัน จึงใช้ `lineUserId` จากการ login ระบุตัวผู้ส่งข้อความในแชทได้ทันที

### โมดูล

| โมดูล | หน้าที่ | ขึ้นกับ |
|---|---|---|
| ตัวแยกข้อความ | `parseMessage(text, { personal, today })` → วันที่และรายการ | ไม่มี (ฟังก์ชันล้วน) |
| พจนานุกรมกลาง | คำ → หมวด ประมาณ 200 คำ | ไม่มี |
| วันที่ไทย | วันนี้/เมื่อวานตามเวลา Asia/Bangkok และแปลง `YYYY-MM-DD` เป็น Timestamp | ไม่มี |
| ตัวเข้ารหัส postback | แปลงข้อมูลการกดปุ่มเป็น string แบบ `a=date&d=…` และแปลงกลับ (ไม่เกิน 300 ตัวอักษร) | ไม่มี |
| ตัวสร้างข้อความตอบ | สร้างการ์ด Flex และ quick reply จากสถานะรายการที่ค้างอยู่ | หมวดหมู่ |
| ตัวจัดการ event | ตัดสินว่าต้องเขียนอะไรและตอบอะไร | รับ store กับ LINE client เป็นพารามิเตอร์ (จึงใส่ตัวปลอมตอนเทสต์ได้) |
| ตัวจำกัดการใช้งาน | ตรวจและเพิ่มตัวนับใน transaction | Firestore |
| OAuth ของ LINE | สร้าง URL, ลงและตรวจลายเซ็น cookie, แลก code, ตรวจ ID token | `fetch`, crypto |
| ไฟล์ใน `api/` | อ่าน request, เรียกโมดูลข้างบน, ส่ง response | ทุกอย่างข้างบน |

โมดูลที่ไม่เรียกเน็ตหรือฐานข้อมูลอยู่ใต้ `src/line/` เพื่อให้ Jest ของ CRA เทสต์ได้ ส่วน `api/` import มาใช้ (ดูข้อ 13 เรื่องที่ต้องยืนยัน)

## 4. ข้อมูล

### คอลเลกชันเดิม

- `transactions`: บอทเขียนด้วย**รูปแบบเดิมทุก field** คือ `userId, amount, type, category, date, note, createdAt` ไม่เพิ่ม field ใหม่ เพราะ rules ระบุชื่อ field ไว้ตายตัว ถ้าเพิ่ม รายการจาก LINE จะแก้ไขบนเว็บไม่ได้
- `date` เก็บแบบเดียวกับ `fromInputDate` ของเว็บ คือเที่ยงวันตามเวลาไทยของวันนั้น (`YYYY-MM-DDT12:00:00+07:00`)
- `budgets/{uid}`: อ่านอย่างเดียวสำหรับ `สรุป` งบของเดือน = `monthly["YYYY-MM"]` ถ้าไม่มีหรือเป็น null ใช้ `budget` (ตรงกับ `budgetFor` ใน `useFinanceData.js`)

### คอลเลกชันใหม่

ใช้ field ชื่อ `userId` เหมือนคอลเลกชันเดิม เพื่อให้ `deleteAllOwned` ในหน้าตั้งค่านำไปใช้ซ้ำได้

| คอลเลกชัน | field | หน้าเว็บ |
|---|---|---|
| `lineLinks/{lineUserId}` | `userId`, `displayName`, `linkedAt` | อ่านและลบได้เฉพาะของตัวเอง |
| `lineDicts/{uid}` | `words: { "<คำ>": "<category key>" }` ไม่เกิน 500 คำ | อ่านและลบได้เฉพาะของตัวเอง |
| `lineDrafts/{messageId}` | ดูด้านล่าง | อ่านและลบได้เฉพาะของตัวเอง |
| `lineUsage/{uid}` | `day, dayCount, minute, minuteCount, warnedDay, warnedMinute, limitPerDay?, limitPerMinute?` | ไม่มีสิทธิ์ |

`lineDrafts/{messageId}`:
```
userId
date: "YYYY-MM-DD" | null            // null = ยังไม่เลือกวัน
status: "awaitingDate" | "open" | "undone" | "cancelled"
items: [{ note, amount, type, category | null, state: "pending" | "saved" | "skipped", txId | null }]
createdAt, expiresAt                 // expiresAt = createdAt + 7 วัน
```

- ใช้ `lineUserId` เป็น id ของ `lineLinks` ทำให้ LINE หนึ่งบัญชีผูกได้กับบัญชีแอปเดียวเท่านั้น
- ใช้ message id ของ LINE เป็น id ของ `lineDrafts` ถ้า LINE ส่ง event ซ้ำ การ `create()` จะล้มเหลวและไม่ทำซ้ำ
- `lineUsage` ใช้ uid เป็น id การยกเลิกเชื่อมแล้วเชื่อมใหม่จึงไม่รีเซ็ตตัวนับ และหน้าเว็บลบไม่ได้ (ถ้าลบได้ก็หลบเกณฑ์ได้) เมื่อลบบัญชี เอกสารนี้จะค้างอยู่ แต่มีแค่ตัวเลขนับ ไม่มีข้อมูลส่วนตัว

### Firestore rules ที่เพิ่ม

```
match /lineLinks/{lineUserId} {
  allow read, delete: if signedIn() && resource.data.userId == request.auth.uid;
}
match /lineDicts/{uid} {
  allow read, delete: if signedIn() && request.auth.uid == uid;
}
match /lineDrafts/{id} {
  allow read, delete: if signedIn() && resource.data.userId == request.auth.uid;
}
// lineUsage: ไม่มี rule = ปฏิเสธทั้งหมด
```

ไม่เปิดให้ create หรือ update ทั้งหมด server เขียนผ่าน admin SDK อย่างเดียว rules ของ `transactions`, `recurring` และ `budgets` ไม่เปลี่ยน

## 5. Login และการเชื่อมบัญชี

### Login หรือสมัครด้วย LINE

1. หน้า `/` และ `/register` มีปุ่มเขียว **"เข้าสู่ระบบด้วย LINE"** อยู่บนสุด ใต้ปุ่มมีเส้นคั่น "หรือใช้อีเมล" ตามด้วยฟอร์มเดิม
2. กดปุ่ม → `POST /api/auth/line/start` ด้วย `{ mode: "login", returnTo? }` → server สุ่ม `state` กับ `nonce` เก็บไว้ใน cookie ที่ลงลายเซ็น HMAC (`HttpOnly; Secure; SameSite=Lax; Path=/api/auth/line; Max-Age=600`) แล้วตอบ `{ url }` → หน้าเว็บสั่ง `window.location = url`
3. URL ของ LINE: `response_type=code`, `scope=openid profile`, `bot_prompt=aggressive` (พอ login เสร็จ LINE จะเปิดหน้าเพิ่มเพื่อนบอทให้), ใส่ `state` กับ `nonce` ไปด้วย
4. `GET /api/auth/line/callback`
   - ตรวจว่า `state` ตรงกับใน cookie แล้วลบ cookie ทิ้ง (ใช้ได้ครั้งเดียว)
   - แลก `code` เป็น token แล้วตรวจ ID token ที่ endpoint verify ของ LINE โดยส่ง `client_id` กับ `nonce` ไปด้วย จะได้ `sub` (= `lineUserId`) และ `name`
   - ถ้ามี `lineLinks/{sub}` อยู่แล้ว ใช้ `userId` ที่ผูกไว้ ถ้ายังไม่มี ใช้ `createUser({ displayName: name })` แล้ว `create()` เอกสาร `lineLinks/{sub}` ถ้า `create()` ล้มเหลวเพราะมีคำขออื่นสร้างไปก่อน ให้ลบผู้ใช้ที่เพิ่งสร้างทิ้งแล้วใช้ของเดิม
   - `createCustomToken(uid)` → redirect ไป `/auth/line#token=<token>&returnTo=<path>`
5. หน้า `/auth/line` (route ใหม่ ไม่ครอบด้วย `PublicRoute` หรือ `PrivateRoute` เพราะต้องใช้ได้ทั้งตอน login ครั้งแรกและตอนที่ login อยู่แล้วแต่ต้องยืนยันตัวตนใหม่) อ่านค่าหลัง `#` แล้ว `history.replaceState` เพื่อล้าง `#` ทันที จากนั้น `signInWithCustomToken` แล้วไปที่ `returnTo` ถ้าไม่มี ไป `/dashboard`

ถ้าเกิดข้อผิดพลาด จะ redirect ไป `/?line_error=<code>` หน้า login แสดงข้อความไทย:

| code | ข้อความ |
|---|---|
| `cancelled` | ยกเลิกการเข้าสู่ระบบด้วย LINE |
| `expired` | ลิงก์หมดอายุ ลองใหม่อีกครั้ง |
| `already_linked` | LINE นี้เชื่อมกับบัญชีอื่นอยู่แล้ว |
| `failed` | เข้าสู่ระบบด้วย LINE ไม่สำเร็จ ลองใหม่อีกครั้ง |

### เชื่อม LINE กับบัญชีอีเมล

- หน้าตั้งค่าเพิ่มส่วน **"LINE"**
- ยังไม่ได้เชื่อม: ปุ่ม **"เชื่อมบัญชี LINE"** และคำอธิบายว่า "เพื่อจดรายรับ-รายจ่ายผ่านแชท LINE" กดแล้วเรียก `start` ด้วย `{ mode: "link" }` และ header `Authorization: Bearer <Firebase ID token>` server ตรวจ ID token แล้วเก็บ uid ไว้ใน cookie ที่ลงลายเซ็น
- `callback` ในโหมด link: ถ้า `lineLinks/{sub}` ผูกกับบัญชีอื่นอยู่ → `already_linked` ไม่รวมข้อมูลให้ ถ้ายังไม่ได้ผูก → `create()` ผูกกับ uid นั้น แล้ว redirect ไป `/settings?line=linked` ไม่ต้องออก token เพราะผู้ใช้ยัง login อยู่
- เชื่อมแล้ว: แสดง "เชื่อมกับ LINE: <ชื่อ>", ปุ่ม **"เพิ่มเพื่อนบอท"** (ลิงก์จาก `REACT_APP_LINE_ADD_FRIEND_URL`) และปุ่ม **"ยกเลิกการเชื่อม"** ซึ่งลบ `lineLinks` จากฝั่งหน้าเว็บ ปุ่มยกเลิกแสดงเฉพาะบัญชีที่มีรหัสผ่าน

### ผู้ใช้ที่ใช้ LINE อย่างเดียว

ดูได้จาก `user.providerData` ที่ไม่มี `providerId === "password"`

- หน้าตั้งค่า: ซ่อน "ยืนยันอีเมล" กับ "เปลี่ยนรหัสผ่าน" แต่แสดงส่วน LINE (ไม่มีปุ่มยกเลิกการเชื่อม)
- Dashboard: ไม่แสดงแถบ "ยังไม่ได้ยืนยันอีเมล"
- **ลบบัญชี**: เหลือแค่พิมพ์ "ลบบัญชี" ไม่ต้องใส่รหัสผ่าน ถ้า `deleteUser` ตอบ `auth/requires-recent-login` จะแสดงปุ่ม "เข้าสู่ระบบด้วย LINE อีกครั้ง" ซึ่งเรียก `start` ด้วย `returnTo=/settings`
- **ลบบัญชีทุกประเภท** (เพิ่มจากที่ลบอยู่แล้ว): ลบ `lineDrafts` และ `lineLinks` ที่ `userId` เป็นของตัวเอง กับ `lineDicts/{uid}` ด้วย
- การหมดอายุของ session ใน `AuthContext` ใช้ได้เหมือนเดิม เพราะ `lastSignInTime` เปลี่ยนเมื่อ login ด้วย custom token ด้วย

## 6. ขั้นตอนในแชท

ปุ่ม quick reply จะหายไปทันทีที่มีข้อความใหม่ในแชท (ตามเอกสาร LINE) ปุ่มที่ต้องกดได้ทีหลังจึงใช้**การ์ด Flex** ที่ปุ่มค้างอยู่ในแชท ส่วน quick reply ใช้เฉพาะตอนเลือกหมวด ซึ่งกดใหม่จากการ์ดได้ถ้าปุ่มหาย ทุกปุ่มใส่ `displayText` ข้อความที่ผู้ใช้กดจึงขึ้นในแชทด้วย ทุกข้อความเป็นการตอบกลับ (reply) ซึ่งไม่นับโควตาข้อความ

### ลำดับการทำงานของ webhook

1. ตรวจ `x-line-signature` (HMAC-SHA256 ของ raw body ด้วย channel secret) ถ้าไม่ผ่าน → 401
2. ทุก event: หา `lineLinks/{source.userId}`
   - ไม่มี: ตอบว่า "ยังไม่ได้เชื่อมบัญชี" พร้อมปุ่ม [เข้าสู่ระบบ / เชื่อมบัญชี] (ลิงก์ไปเว็บ) ไม่เขียนอะไร
   - มี: ผ่านตัวจำกัดการใช้งาน (ข้อ 8) ก่อน แล้วไปทำตามประเภท event
3. ตอบ 200 เสมอเมื่อลายเซ็นถูก

### event `follow` (เพิ่มเพื่อน)

- เชื่อมบัญชีแล้ว: ทักทายและบอกตัวอย่างการพิมพ์
- ยังไม่เชื่อม: ทักทายพร้อมปุ่มเชื่อมบัญชี

### ข้อความ

| ข้อความ | ทำอะไร |
|---|---|
| `สรุป`, `เดือนนี้`, `สรุปเดือนนี้` | ตอบสรุปเดือนปัจจุบัน |
| `วิธีใช้`, `help` | ตอบตัวอย่างการพิมพ์ |
| อื่น ๆ | ส่งเข้าตัวแยกข้อความ |

ผลจากตัวแยกข้อความ:

- **ไม่มีรายการ** (ไม่เจอจำนวนเงิน): ตอบตัวอย่างการพิมพ์ ไม่สร้างรายการค้าง
- **error** (วันในอนาคต, เกิน 10 รายการ, จำนวนเงินเกินกำหนด): ตอบเหตุผลเป็นภาษาไทย
- **มีรายการ แต่ไม่ได้ระบุวัน**: สร้าง `lineDrafts` สถานะ `awaitingDate` แล้วส่ง**การ์ดถามวัน**
- **มีรายการและระบุวันแล้ว**: สร้าง `lineDrafts` แล้วทำขั้นบันทึกต่อทันที (เหมือนกดวัน)

ก่อนสร้างรายการค้างใหม่ทุกครั้ง ลบรายการค้างของผู้ใช้คนนี้ที่ `expiresAt` ผ่านไปแล้ว

**การ์ดถามวัน:** แสดงรายการพร้อมจำนวนเงินและหมวดที่เดาได้ รายการที่ยังไม่รู้หมวดแสดง "?" ด้านล่างมีปุ่ม `[วันนี้] [เมื่อวาน] [เลือกวัน…] [ยกเลิก]` ปุ่ม "เลือกวัน…" เป็น datetimepicker โหมด `date` ตั้ง `max` เป็นวันนี้ตามเวลาไทย

### การกดปุ่ม (postback)

data มีรูปแบบ `a=<action>&d=<draftId>[&i=<index>][&c=<category>][&v=<value>]`

| action | ทำได้เมื่อ | ทำอะไร |
|---|---|---|
| `date` | `awaitingDate` | ตั้งวันที่ (`v=today` หรือ `v=yesterday` หรือใช้ `postback.params.date`) แล้วเข้าขั้นบันทึก |
| `cancel` | `awaitingDate` | เปลี่ยนเป็น `cancelled` แล้วตอบ "ยกเลิกแล้ว" |
| `ask` | `open` และรายการ `i` ยังเป็น `pending` | ส่ง quick reply เลือกหมวดของรายการ `i` |
| `cat` | `open` และรายการ `i` เป็น `pending` | บันทึกรายการ `i` ด้วยหมวด `c` และจำคำ แล้วถามรายการ pending ถัดไป ถ้าไม่เหลือ ส่งการ์ดสรุป |
| `skip` | `open` และรายการ `i` เป็น `pending` | เปลี่ยนรายการ `i` เป็น `skipped` |
| `fix` | `open` | ไม่มี `i`: ส่ง quick reply ให้เลือกรายการที่บันทึกแล้ว มี `i`: ส่ง quick reply เลือกหมวด |
| `fixcat` | `open` และรายการ `i` เป็น `saved` | อัปเดต `category` และ `type` ของรายการนั้นใน `transactions` และจำคำ |
| `types` | ทุกครั้งที่มีการเลือกหมวด | สลับรายการหมวดใน quick reply ระหว่างรายจ่ายกับรายรับ |
| `undo` | `open` | ลบทุก `txId` ที่ยังอยู่ แล้วเปลี่ยนเป็น `undone` |

- ถ้าสถานะไม่ตรงตามคอลัมน์ "ทำได้เมื่อ" (เช่น กดวันซ้ำ หรือกดหลังเลิกทำ) ตอบตามสถานะจริง เช่น "บันทึกไปแล้ว" หรือ "ยกเลิกไปแล้ว" และไม่เขียนอะไร
- ถ้า `expiresAt` ผ่านไปแล้ว ตอบ "รายการนี้หมดอายุแล้ว พิมพ์ใหม่อีกครั้ง"
- **ขั้นบันทึก**: ทำใน transaction เดียว คือสร้าง `transactions` ของทุกรายการที่มีหมวด เก็บ `txId`, ตั้ง `state: saved`, ตั้ง `status: open` แล้วส่ง**การ์ดสรุป**
- **การ์ดสรุป**: "✓ บันทึกแล้ว N รายการ · <วัน> · รวม X บาท" ตามด้วยรายการที่บันทึก และรายการที่รอเลือกหมวด ซึ่งแต่ละรายการมีปุ่ม `[เลือกหมวด]` (action `ask`) ด้านล่างมีปุ่ม `[แก้หมวด] [เลิกทำ]` ถ้ามีรายการรอเลือกหมวด จะส่ง quick reply ของรายการแรกมาพร้อมการ์ดเลย
- **quick reply เลือกหมวด**: หมวดรายจ่าย 9 ปุ่ม + `รายรับ…` + `ไม่บันทึก` (รวม 11) หรือหมวดรายรับ 4 ปุ่ม + `รายจ่าย…` + `ไม่บันทึก` ป้ายปุ่มต้องไม่เกิน 20 ตัวอักษร จึงใช้ชื่อย่อเฉพาะใน LINE เช่น "ค่าน้ำ/ไฟ/เน็ต/โทรศัพท์" → "น้ำ/ไฟ/เน็ต/โทร" ส่วน `fix` ไม่มีปุ่ม `ไม่บันทึก`
- "จำคำ" = ตั้ง `lineDicts/{uid}.words[<คำอธิบายที่ตัดช่องว่างแล้ว ไม่เกิน 30 ตัวอักษร>] = category` ถ้าครบ 500 คำแล้วจะไม่เพิ่มคำใหม่ แต่แก้คำเดิมได้

### คำสั่ง `สรุป`

ตอบข้อมูลของเดือนปัจจุบันตามเวลาไทย: รายรับ, รายจ่าย, คงเหลือ ถ้าตั้งงบไว้จะเพิ่ม "ใช้ไป N% ของงบ เหลือ X บาท" (หรือ "เกินงบ X บาท") พร้อมปุ่ม [เปิดเว็บ] ข้อมูลมาจาก query `transactions` ที่ `userId == uid` และ `date` อยู่ในช่วงเดือนนั้น และจาก `budgets/{uid}` query นี้ต้องใช้ **composite index ใหม่** (`userId` ASC, `date` ASC) เพราะหน้าเว็บ query แค่ `userId ==` จึงยังไม่มี index นี้ (ดูข้อ 12)

## 7. ตัวแยกข้อความ

```
parseMessage(text, { personal = {}, today }) →
  { date: "YYYY-MM-DD" | null, items: [{ note, amount, type, category | null }], error?: string }
```

`today` ส่งเข้ามาเป็น `"YYYY-MM-DD"` เพื่อให้เทสต์ได้โดยไม่ขึ้นกับเวลาจริง

1. **ปรับรูปแบบ**: เลขไทย ๐–๙ เป็น 0–9, ตัดจุลภาคในตัวเลข, ขึ้นบรรทัดใหม่และเว้นวรรคหลายตัวถือเป็นช่องว่างเดียว
2. **วันที่** (ดูเฉพาะต้นข้อความ):
   - รับ `วันนี้`, `เมื่อวาน`, `เมื่อวานซืน`, `d/m`, `d/m/yyyy` และ `d <เดือนย่อหรือเต็ม>` เช่น `12 ต.ค.` หรือ `12 ตุลาคม`
   - ปีที่เกิน 2400 ถือเป็น พ.ศ. ถ้าไม่ระบุปี ใช้ปีนี้ แต่ถ้าวันนั้นยังมาไม่ถึง ให้เป็นปีที่แล้ว
   - วันในอนาคตหรือวันที่ไม่มีจริงเป็น error
3. **จำนวนเงิน**:
   - ตัวเลขจำนวนเต็มหรือทศนิยมไม่เกิน 2 ตำแหน่ง อาจมี `฿` นำหน้า หรือ `บาท`, `บ.`, `บ`, `.-`, `k`/`K` (×1000) ต่อท้าย
   - ตัวเลขที่ติดกับตัวอักษร (`5G`) ไม่ใช่จำนวนเงิน ตัวเลขที่มีลักษณนามตามหลัง (จาน แก้ว ชิ้น ขวด ห่อ กล่อง คน ลิตร อัน ใบ ตัว เล่ม) ก็ไม่ใช่ และถือเป็นส่วนหนึ่งของคำอธิบาย
   - `+` หน้าตัวเลขแปลว่ารายรับ
4. **ตัดเป็นรายการ**: ปกติคำอธิบายคือข้อความระหว่างจำนวนเงินก่อนหน้ากับจำนวนเงินของรายการนั้น ถ้าข้อความ (หลังส่วนวันที่) ขึ้นต้นด้วยจำนวนเงิน ให้ใช้ข้อความ**หลัง**จำนวนเงินเป็นคำอธิบายแทน ตัดเครื่องหมายคั่น (`,` `/` `+` `และ`) ที่หัวท้ายของคำอธิบายออก
5. **ข้อจำกัด**:
   - จำนวนเงินต้องมากกว่า 0 และไม่เกิน 1,000,000,000
   - คำอธิบายเกิน 100 ตัวอักษรจะถูกตัด
   - ข้อความหนึ่งมีได้ไม่เกิน **10 รายการ** (quick reply ตอนแก้หมวดมีได้ 13 ปุ่ม) ถ้าเกินเป็น error ให้แยกส่ง
6. **หมวด**:
   - เอาคำอธิบายมาทำตัวพิมพ์เล็กและตัดช่องว่างออก
   - ค้นพจนานุกรมส่วนตัวก่อน เลือกคำที่ยาวที่สุดที่อยู่ในคำอธิบาย ถ้าไม่เจอ ค้นพจนานุกรมกลางแบบเดียวกัน ถ้าไม่เจอทั้งสองที่ → `null`
   - คำที่ยาวเท่ากันและชนกันต้องมีคำรวมในพจนานุกรมกลาง เช่น `ค่าน้ำมัน` → `travel` มีเทสต์คุมทุกคู่ที่รู้
7. **ประเภท**:
   - หมวด `salary`, `bonus`, `freelance`, `income` → `income`
   - คำอธิบายขึ้นต้นด้วย `ได้` หรือ `รับ` หรือมี `+` นำหน้าตัวเลข → `income` ถ้าหมวดที่จับได้เป็นหมวดรายจ่าย ให้เปลี่ยนเป็น `income` (รายรับอื่นๆ)
   - กรณีอื่นเป็น `expense`

## 8. จำกัดการใช้งาน

นับทุก event ที่ทำให้ระบบทำงาน (ข้อความและการกดปุ่ม) ของผู้ใช้ที่เชื่อมบัญชีแล้ว

| ชั้น | ค่าเริ่มต้น | env | เกินแล้ว |
|---|---|---|---|
| ต่อนาที | 20 | `LINE_LIMIT_PER_MINUTE` | "ส่งเร็วเกินไป รอสักครู่แล้วลองใหม่" |
| ต่อวัน (เริ่มนับใหม่ตอนเที่ยงคืนเวลาไทย) | 300 | `LINE_LIMIT_PER_DAY` | "วันนี้ใช้ครบแล้ว จดต่อได้ที่เว็บ" + [เปิดเว็บ] |

- ใช้ Firestore transaction บน `lineUsage/{uid}` อ่านตัวนับ ถ้าเปลี่ยนนาทีหรือเปลี่ยนวันแล้วให้รีเซ็ต ถ้ายังไม่เกินให้ +1 แล้วทำงานต่อ
- ข้อความเตือนส่ง**ครั้งเดียวต่อช่วง** (ใช้ `warnedMinute` และ `warnedDay` เก็บว่าเตือนไปแล้ว) หลังจากนั้นเมินเงียบ ไม่ตอบและไม่เขียนอะไร
- `undo` และ `cancel` **ไม่ถูกจำกัด** และไม่นับ เพราะทำได้ครั้งเดียวต่อรายการค้างอยู่แล้ว
- ปรับเป็นรายคนได้โดยใส่ `limitPerDay` หรือ `limitPerMinute` ใน `lineUsage/{uid}` ผ่าน Firebase Console ใส่ `0` เพื่อระงับการใช้บอท
- ผู้ใช้ที่ยังไม่เชื่อมบัญชีไม่ถูกนับ เพราะแต่ละ event ใช้แค่การอ่าน 1 ครั้งและไม่เขียนอะไร

## 9. การจัดการข้อผิดพลาด

- **Webhook**: ถ้าเกิด error ระหว่างประมวลผล ให้เก็บ log (`console.error` ไม่ใส่ข้อความของผู้ใช้หรือ token) แล้วพยายามตอบ "ขออภัย ระบบขัดข้อง ลองใหม่อีกครั้ง" และตอบ 200 ให้ LINE
- **การเขียนข้อมูล**: การเปลี่ยนสถานะรายการค้างกับการเขียน `transactions` อยู่ใน transaction เดียวกันเสมอ
- **Reply token**: ทำงานให้จบใน request เดียว ไม่ใช้ push
- **Login**: ทุกกรณีที่ผิดพลาด redirect ไปพร้อม `line_error` ตามตารางในข้อ 5 รายละเอียดเก็บไว้แค่ใน log ของ server
- **หน้า `/auth/line`**: ถ้าไม่มี token หรือ `signInWithCustomToken` ล้มเหลว ให้กลับไป `/?line_error=failed`

## 10. ความปลอดภัย

- ตรวจลายเซ็น webhook ทุก request ด้วยการเปรียบเทียบแบบ constant-time (`crypto.timingSafeEqual`)
- OAuth: ใช้ `state` กับ `nonce` แบบสุ่ม 32 ไบต์, cookie ลงลายเซ็น HMAC-SHA256 ด้วย `AUTH_COOKIE_SECRET` ที่มีเวลาหมดอายุในตัว ใช้ได้ครั้งเดียว และตรวจ ID token กับ LINE ทุกครั้ง
- `start` ในโหมด link ต้องมี Firebase ID token ที่ผ่าน `verifyIdToken`
- custom token อยู่หลัง `#` เท่านั้น และถูกล้างออกจาก URL ก่อน sign in
- `returnTo` รับเฉพาะ path ภายในที่ขึ้นต้นด้วย `/` แต่ไม่ใช่ `//` กัน open redirect
- ค่าลับทั้งหมดอยู่ใน env ของ Vercel และ `.env.local` ซึ่ง `.gitignore` ครอบไว้แล้ว ไม่เก็บใน repo
- CSP ใน `vercel.json` ไม่ต้องแก้ เพราะการไปหน้า LINE เป็นการเปลี่ยนหน้า ไม่ใช่การส่งฟอร์ม และ `fetch` ไป `/api` เป็น `self`

## 11. การทดสอบ

**Jest** (ใช้ `npm test` ที่มีอยู่):
- ตัวแยกข้อความประมาณ 60 กรณี: ตัวอย่างใน spec, เลขไทย, จุลภาค, `k`, `฿`, `.-`, ลักษณนาม, `5G`, ขึ้นต้นด้วยตัวเลข, รายรับปนรายจ่าย, `+`, วันที่ทุกรูปแบบ, ปี พ.ศ., วันในอนาคต, วันที่ไม่มีจริง, เกิน 10 รายการ, ไม่มีตัวเลข, คำชนกัน และการใช้พจนานุกรมส่วนตัวก่อนพจนานุกรมกลาง
- วันที่ไทย: ช่วงรอยต่อเที่ยงคืน (UTC 17:00) และรอยต่อเดือนหรือปี
- ตัวเข้ารหัส postback: แปลงไปแล้วแปลงกลับได้ค่าเดิม และยาวไม่เกิน 300 ตัวอักษร
- ตัวจัดการ event (ใช้ store กับ LINE client ปลอม): ทุก action ในตารางข้อ 6, การกดซ้ำ, การหมดอายุ, ผู้ใช้ที่ยังไม่เชื่อมบัญชี และตัวจำกัดการใช้งาน (เกินเกณฑ์, เตือนครั้งเดียว, undo ผ่านได้เสมอ, ค่ารายคน)
- ตรวจลายเซ็น webhook และลงหรือตรวจลายเซ็น cookie (ถูก, ผิด, หมดอายุ)
- ตัวสร้างข้อความ: ป้ายปุ่ม quick reply ไม่เกิน 20 ตัวอักษร และไม่เกิน 13 ปุ่ม

**ทดสอบจริงบน Vercel preview** (URL ของ branch ไม่เปลี่ยน ใช้ลงทะเบียนใน LINE ได้):
login ใหม่ด้วย LINE → เพิ่มเพื่อนบอท → ส่งข้อความ 3 รายการ → เลือกวัน → คำที่ไม่รู้จัก → แก้หมวด → เลิกทำ → `สรุป` → เชื่อม LINE กับบัญชีอีเมล → เชื่อมซ้ำกับบัญชีอื่น → ยกเลิกการเชื่อม → ส่งรัวให้เกินเกณฑ์ → ลบบัญชี LINE อย่างเดียว

ก่อน push ต้องผ่าน `CI=true npm run build` และให้ agent `security-reviewer` กับ `usability-reviewer` ตรวจ

## 12. สิ่งที่เจ้าของโปรเจกต์ต้องตั้งค่าเอง

เขียนขั้นตอนละเอียดไว้ใน README ส่วน "ตั้งค่า LINE":

1. **LINE Developers Console**
   - สร้าง Provider
   - สร้าง LINE Login channel ใต้ Provider นั้น ใส่ callback URL ของ production, preview และ `http://localhost:3000/api/auth/line/callback`
   - สร้าง Messaging API channel (LINE Official Account) ใต้ **Provider เดียวกัน** ตั้ง webhook URL เป็น `https://<โดเมน>/api/line/webhook` และเปิด Use webhook
   - ผูก Official Account เข้ากับ LINE Login channel (ต้องผูกถึงจะใช้ `bot_prompt` ได้)
2. **LINE Official Account Manager**: ปิดข้อความตอบกลับอัตโนมัติและข้อความทักทายของ OA
3. **Firebase Console**: สร้างคีย์ service account (Project settings → Service accounts)
4. **Vercel → Environment Variables**:
   `LINE_LOGIN_CHANNEL_ID`, `LINE_LOGIN_CHANNEL_SECRET`, `LINE_CHANNEL_SECRET`, `LINE_CHANNEL_ACCESS_TOKEN`, `FIREBASE_SERVICE_ACCOUNT` (JSON), `AUTH_COOKIE_SECRET`, `LINE_LIMIT_PER_MINUTE`, `LINE_LIMIT_PER_DAY` (สองตัวนี้ไม่ใส่ก็ได้), `REACT_APP_LINE_ADD_FRIEND_URL`
5. วาง `firestore.rules` ใหม่ใน Firebase Console แล้วกด Publish
6. สร้าง composite index 2 ตัวใน Firebase Console → Firestore → Indexes (หรือกดลิงก์ที่ Firestore แนบมากับ error ใน log ครั้งแรกที่ query)
   - `transactions`: `userId` ASC, `date` ASC (ใช้กับคำสั่ง `สรุป`)
   - `lineDrafts`: `userId` ASC, `expiresAt` ASC (ใช้ลบรายการค้างที่หมดอายุ)

- README ส่วน "ลองใช้": เพิ่มวิธีลองบอท ส่วนคนที่ไม่มี LINE ยังลองผ่านอีเมลได้เหมือนเดิม
- `PRODUCT.md`: เพิ่มใน Capabilities, Routes (`/auth/line`) และ Stack (Vercel Functions)

## 13. ลำดับการสร้างและเรื่องที่ต้องยืนยันตอนวางแผน

**ลำดับ** (แต่ละช่วงเสร็จแล้วใช้งานได้จริง):
1. **LINE Login และการเชื่อมบัญชี**: `api/auth/line/*`, `/auth/line`, ปุ่มที่หน้า login และ register, ส่วน LINE ในหน้าตั้งค่า, การปรับสำหรับผู้ใช้ LINE อย่างเดียว, rules ของ `lineLinks`
2. **ตัวแยกข้อความกับพจนานุกรม**: โมดูลล้วนพร้อมเทสต์ ยังไม่ต่อกับ LINE
3. **บอท**: webhook, รายการค้าง, การ์ด, หมวด, การจำคำ, `สรุป`, ตัวจำกัดการใช้งาน, rules ที่เหลือ และเอกสาร

**เรื่องที่ต้องยืนยันตอนวางแผน** (เลือกทางหลักไว้แล้ว และมีทางสำรอง):
- **การ import โค้ดจาก `src/line/` ไปใช้ใน `api/`**: ทางหลักคือให้ Vercel bundle ESM ข้ามโฟลเดอร์ให้ ทางสำรองคือย้ายโมดูลล้วนไปไว้ในโฟลเดอร์ที่ทั้งสองฝั่งใช้ได้ และตั้ง Jest `roots` เพิ่ม
- **การอ่าน raw body ใน Vercel Function** เพื่อตรวจลายเซ็น: ทางหลักคือใช้ function แบบ Web `Request` แล้วเรียก `request.text()`
- การรัน `api/` บนเครื่องด้วย `vercel dev` และใช้ tunnel เพื่อรับ webhook ตอนพัฒนา
